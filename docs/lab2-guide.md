# Инструкция к лабораторной работе 2

Версия 2, 19.09.2026. Вариант 24: внутренние закупки организации. Это учебный локальный сервис. Он хранит данные в памяти, поэтому после остановки все созданные записи исчезают. Используйте вымышленные данные.

## Как устроен результат

Клиент отправляет JSON в один из пяти контроллеров `*Controller` в папке `src/main/java/ru/rbpo/lab1/procurement`. Контроллер выбирает HTTP-маршрут и вызывает `ProcurementService`. Сервис проверяет обязательные поля, существование ссылок и допустимость удаления. `InMemoryProcurementRepository` хранит пять коллекций. `ProcurementClockConfiguration` передаёт серверные часы для `createdAt` и `updatedAt`; клиент эти поля не задаёт.

Пример: пользователь с `id=1` создаёт заявку с `authorId=1` и `maxAmount=1200.50`. Сервер возвращает заявку с новым `id` и временем. Поставщик и предложение ссылаются на эту заявку; заказ выбирает предложение. Пока заказ существует, удаление предложения даёт HTTP 409, а предложение остаётся в списке.

## Пользователю: создать и посмотреть записи

Цель: пройти одну цепочку от пользователя до заказа. Доступ: локальный компьютер с JDK 17+ и PowerShell; пароль сервис не запрашивает. Рабочая папка:

```powershell
cd 'C:\Users\satur\Desktop\ТОХИР\Учёба МТУСИ\5 семестр\РБПО\Код'
java -version
.\mvnw.cmd verify
java -jar target\lab1-1.0.0.jar --server.port=18080
```

Ожидается `BUILD SUCCESS` и 9 тестов без ошибок; сервер слушает `127.0.0.1:18080`. Оставьте это окно открытым. Во втором окне PowerShell выполните:

```powershell
$base = 'http://127.0.0.1:18080'
$user = Invoke-RestMethod -Uri "$base/api/users" -Method Post -ContentType 'application/json' -Body '{"name":"Ирина"}'
$requestBody = @{authorId=$user.id; description='Бумага'; maxAmount=1200.50; status='Новая'} | ConvertTo-Json -Compress
$request = Invoke-RestMethod -Uri "$base/api/purchase-requests" -Method Post -ContentType 'application/json' -Body $requestBody
$supplier = Invoke-RestMethod -Uri "$base/api/suppliers" -Method Post -ContentType 'application/json' -Body '{"name":"Поставка","category":"Канцелярия","admitted":true}'
$offerBody = @{purchaseRequestId=$request.id; supplierId=$supplier.id; price=900.25; deliveryDays=5; validityDays=14} | ConvertTo-Json -Compress
$offer = Invoke-RestMethod -Uri "$base/api/commercial-offers" -Method Post -ContentType 'application/json' -Body $offerBody
$orderBody = @{purchaseRequestId=$request.id; selectedOfferId=$offer.id; fulfillmentStatus='Создан'} | ConvertTo-Json -Compress
$order = Invoke-RestMethod -Uri "$base/api/purchase-orders" -Method Post -ContentType 'application/json' -Body $orderBody
Invoke-RestMethod -Uri "$base/api/purchase-orders/$($order.id)"
```

Каждое создание возвращает запись с числовым `id` и временем сервера. Последняя команда должна вернуть заказ с `purchaseRequestId=$request.id` и `selectedOfferId=$offer.id`. В пустом процессе первый `id` каждого вида равен 1; после других запросов используйте значения переменных, а не предполагаемый номер. Для просмотра списка замените последний адрес на `$base/api/purchase-orders`.

Цель частичного изменения: поменять только статус заявки. В том же втором окне:

```powershell
$body = @{status='Согласована'} | ConvertTo-Json -Compress
Invoke-RestMethod -Uri "$base/api/purchase-requests/$($request.id)" -Method Patch -ContentType 'application/json' -Body $body
```

Ожидается HTTP 200: статус изменится, автор, описание и сумма сохранятся. При `PATCH` не передавайте `id`, время, лишние поля или явный `null`: сервер вернёт 400. Несуществующий `id` или ссылка даёт 404. Попытка удалить предложение, на которое ссылается заказ, даёт 409. Ответы ошибок содержат `error` и `message`; 400 означает неверный ввод, 404 — отсутствующую запись, 409 — конфликт связей.

Для безопасного удаления сначала удалите заказ, затем предложение, заявку и поставщика, затем пользователя. Каждый успешный `DELETE` возвращает 204 без тела. Остановите сервер сочетанием `Ctrl+C` в первом окне. Если запрос не соединяется, проверьте, что процесс запущен и порт тот же. Если порт занят, выберите другой свободный номер и замените его в `$base`. Если проверка Maven не прошла, смотрите `target/surefire-reports`, исправьте причину и повторите `verify` до запуска.

## Администратору: настройки и восстановление

Цель: запустить учебный сервис локально и понять состояние. Доступ: изменение файлов проекта и JDK 17+. Настройки находятся в `src/main/resources/application.yml`:

| Настройка | Тип и значение в проекте | Проверка |
| --- | --- | --- |
| `spring.application.name` | строка `1БКС24106` | тест `applicationNameMatchesTicket` |
| `spring.jackson.deserialization.fail-on-unknown-properties` | логическое `true` | лишнее поле даёт 400 |
| `spring.jackson.deserialization.use-big-decimal-for-floats` | логическое `true` | тест точной денежной суммы |
| `server.address` | адрес `127.0.0.1` | сокет слушает только локальный адрес |

Значения действуют после перезапуска. Порт по умолчанию 8080; параметр `--server.port=18080` меняет его только для данного запуска. Интерфейса управления настройками, журнала изменений и резервного копирования данных нет.

Проверка доступности: из рабочей папки после запуска выполните `Invoke-RestMethod http://127.0.0.1:18080/api/users`. Пустой массив `[]` означает работающий сервер без записей; ошибка соединения означает, что сервер или порт недоступен. Отдельного показателя свежести данных нет: все записи принадлежат текущему процессу. В логах запуска видно адрес и порт прослушивания; технические результаты тестов находятся в `target/surefire-reports`.

Для возврата после неудачной локальной правки восстановите изменённые файлы из сохранённой копии или предыдущего коммита, выполните `.\mvnw.cmd verify` и перезапустите приложение. Перед публичным откатом коммита смотрите `git log --oneline`; используйте `git revert <хеш-коммита>` из корня проекта и повторите `verify`. Процедура публичного отката не выполнялась; данные текущего процесса при любом перезапуске теряются. Не меняйте `server.address` для доступа из сети без отдельной защиты входа и прав.

## Разработчику: добавить поле заявки

Цель: например, добавить необязательное текстовое поле `department` к заявке. Доступ: исходники проекта, JDK 17+, знание Java. Это конкретная точка расширения, а не уже реализованное поле. Читайте по маршруту: [LabApplication](../src/main/java/ru/rbpo/lab1/LabApplication.java) → [PurchaseRequestsController](../src/main/java/ru/rbpo/lab1/procurement/PurchaseRequestsController.java) → [ProcurementService](../src/main/java/ru/rbpo/lab1/procurement/ProcurementService.java) → [InMemoryProcurementRepository](../src/main/java/ru/rbpo/lab1/procurement/InMemoryProcurementRepository.java). Модели ввода и ответа находятся в [ProcurementModels](../src/main/java/ru/rbpo/lab1/procurement/ProcurementModels.java). Такой маршрут позволяет увидеть путь от JSON до хранилища без чтения всего проекта.

1. Сохраните текущий коммит или отдельную копию. В `ProcurementModels.PurchaseRequest` добавьте `String department`, а в `PurchaseRequestInput` — одноимённое поле. В `PurchaseRequestInput.fromJson` разрешите ключ и читайте его через `InputJson.text`.
2. В `ProcurementService.createPurchaseRequest` передайте значение в новую запись. В `updatePurchaseRequest` берите новое значение, если оно передано, иначе сохраняйте прежнее. В этом примере однажды заданное поле не очищается: общий контракт запрещает явный `null`. Если нужна очистка, сначала определите отдельный допустимый способ в спецификации и тесте. Если поле должно быть обязательным, добавьте проверку там же и опишите совместимость старых запросов.
3. HTTP-маршруты в `PurchaseRequestsController` менять не требуется, если меняются только поля JSON. Дополните `ProcurementApiTest.completeResourceLifecycle` проверками создания, чтения и частичного изменения, а также проверкой неверного типа. Сохраните прежние проверки.
4. Обновите таблицу полей и пример в [спецификации](spec-v2.md), метод M-09–M-13 и M2-INPUT в корневом README, этот пример, отчёт при сдаче и запись в [журнале](state-lab2.md). Если новый параметр требует настройки, укажите её тип, значение по умолчанию и проверку в `application.yml`.
5. Из корня проекта выполните `.\mvnw.cmd verify`. Ожидаются все прежние 9 тестов и новые проверки без ошибок; затем запустите JAR и проверьте новый JSON реальным запросом. Если изменён опубликованный контракт, согласуйте изменение клиента, пересоберите и отправьте новую версию. Для отката восстановите сохранённый коммит и снова выполните `verify`.

Новая зависимость обычно не нужна. Если она всё же добавлена, проверьте её версию и транзитивные зависимости. Не используйте реальные закупочные или персональные данные: вход по паролю, разграничение прав и постоянное хранение здесь не реализованы.
