# РБПО — лабораторная работа 1

Версия 1.0.0, 2026-09-19. Владелец роли: студент, сдающий лабораторную работу. Проект — небольшое публичное Java-приложение на Spring Boot 3.5.16, Jetty и Maven. Оно возвращает разные JSON-ответы по двум GET-адресам. [Спецификация v1](docs/spec-v1.md) фиксирует требования задания и приёмочные сценарии; [проверка безопасности v1](docs/security-v1.md) фиксирует затронутую поверхность и проверку зависимостей.

Публичный репозиторий проекта: [Rengen34/rbpo-lab1](https://github.com/Rengen34/rbpo-lab1).

Источник видимых требований: [раздел «Задание 1» в репозитории преподавателя](https://github.com/MatorinFedor/RBPO-ZIOVPO-2026#задание-1-подготовка-репозитория) и связанный с ним `files/zadanie1.pdf`. Скачанный оттуда PDF побайтово совпадает с полученным для работы файлом (SHA-256 `638A5BDB76A39E8D02CA06ED8262850404F4A8470E6B9D0D6D3EFDD0B51B1FF4`). Раздел «Задание 2» относится к другой работе.

## Быстрый маршрут по проекту

За 30–60 минут начните с [pom.xml](pom.xml) (версия Java и зависимости), затем откройте [LabApplication.main](src/main/java/ru/rbpo/lab1/LabApplication.java) (точка входа), [LabController.message и LabController.numbers](src/main/java/ru/rbpo/lab1/LabController.java) (правила ответов), [application.yml](src/main/resources/application.yml) (номер билета) и [LabControllerTest](src/test/java/ru/rbpo/lab1/LabControllerTest.java) (проверки запросов). Команды запуска и диагностика находятся ниже. Это авторский маршрут чтения; независимый новичок пока не проверял, укладывается ли он в 30–60 минут.

## Паспорт продукта

| Поле | Фактическое состояние |
| --- | --- |
| Назначение | Демонстрация Java, Spring Boot, Maven и двух GET-маршрутов |
| Источники данных | Внешних источников нет; оба ответа заданы в `LabController` |
| Обновление и часовой пояс | Автоматического обновления и зависимости от часового пояса нет |
| Правила и формулы | Маршрут `message` возвращает строку; `numbers` возвращает `[1,2,3]`; расчётов и округления нет |
| Исключения и отсутствующие данные | Пользовательские данные не принимаются; неизвестный маршрут даёт HTTP 404 |
| Настройка | `spring.application.name` — строка `1БКС24106`; действует после перезапуска |
| Хранение и доступ | Базы данных и учётных записей нет; локальный HTTP API обслуживает Jetty на порту 8080 |
| Ограничения | Учебный сервис возвращает статические данные; GitHub и ЛМС управляются отдельно |

Пример пути «вход → правило → результат»: браузер отправляет `GET http://localhost:8080/api/numbers`; Spring MVC передаёт запрос в `LabController.numbers`; метод создаёт неизменяемый список `1, 2, 3`; клиент получает `{"numbers":[1,2,3]}`. Настройка имени приложения на этот ответ не влияет.

## Реестр методов и формул

| ID | Файл и символ | Контракт | Требование и проверка |
| --- | --- | --- | --- |
| M-01 | `LabApplication.main` | Запускает Spring Boot с аргументами командной строки; открывает HTTP-сервер | R1/R2/R4, контекст и `applicationNameMatchesTicket` в `LabControllerTest` |
| M-02 | `LabController.message` | `GET /api/message` → `200`, `{"message":"Проект работает"}` | R3, `messageReturnsJsonText` |
| M-03 | `LabController.numbers` | `GET /api/numbers` → `200`, `{"numbers":[1,2,3]}` | R3, `numbersReturnsJsonArray` |

Формул нет: приложение не вычисляет показатели. Сценарий неизвестного пути проверяет `unknownPathReturnsNotFound`. Java-методы и их Javadoc ссылаются на эти ID.

## Руководство пользователя

Цель: проверить два адреса приложения. Доступ: компьютер с запущенным приложением и доступ к `localhost:8080`; учётная запись не нужна. Предусловия: выполнен запуск из раздела «Эксплуатация» ниже.

1. Откройте `http://localhost:8080/api/message` в браузере. Ожидается JSON `{"message":"Проект работает"}`.
2. Откройте `http://localhost:8080/api/numbers`. Ожидается JSON `{"numbers":[1,2,3]}`.
3. Для проверки ошибки откройте `http://localhost:8080/api/unknown`. Ожидается HTTP 404, а не один из успешных ответов.

Если браузер не подключается, проверьте, что процесс ещё работает и порт 8080 не занят другим приложением. Если виден неожиданный ответ, запустите тесты из следующего раздела и сверьте маршруты с реестром методов. Эти шаги можно повторять без изменения данных.

## Руководство администратора и эксплуатации

### Подготовка и безопасная проверка

Цель: собрать проект и убедиться, что HTTP-контракт не нарушен. Доступ: локальная копия репозитория, JDK 17 или новее, интернет при первом запуске Maven Wrapper. Команды ниже выполняются в PowerShell из папки `Код`, где лежит `pom.xml`.

1. Проверьте Java: `java -version` и `javac -version`. Если команд нет, установите JDK 21 по [официальной инструкции Eclipse Temurin](https://adoptium.net/installation) и откройте новый PowerShell. Версии должны начинаться с `21` либо быть другой поддерживаемой версией 17–25.
2. Проверьте Maven Wrapper: `.\mvnw.cmd -version`. При первом запуске он скачает Maven 3.9.16; его SHA-256 закреплён в `.mvn/wrapper/maven-wrapper.properties`.
3. Запустите проверки: `.\mvnw.cmd -B -ntp test`. Ожидается `BUILD SUCCESS`: три HTTP-теста и одна проверка номера билета.
4. Запустите приложение: `.\mvnw.cmd -B -ntp spring-boot:run`. Дождитесь `Started LabApplication`.
5. В другом PowerShell выполните `Invoke-RestMethod http://localhost:8080/api/message` и `Invoke-RestMethod http://localhost:8080/api/numbers`. Сверьте значения с реестром методов. Остановите сервер `Ctrl+C` в первом окне.

Если Maven не может скачать зависимости, проверьте интернет и повторите команду после восстановления связи; не изменяйте версии вслепую. Если порт 8080 занят, остановите другой процесс или запустите `./mvnw.cmd -B -ntp spring-boot:run '-Dspring-boot.run.arguments=--server.port=8081'` и проверяйте порт 8081. Если тесты падают, смотрите `target/surefire-reports/`. Сборка не отправляет сообщения и не меняет внешние данные; откат локальной сборки — удалить каталог `target/`.

### Настройка и восстановление

Цель: указать номер билета в имени приложения. Доступ: право редактировать исходники. Единственный рабочий источник этого параметра — `src/main/resources/application.yml`; тип — строка, значение по умолчанию не используется. Перед изменением сохраните предыдущую версию файлов через Git. Затем измените `spring.application.name` и ожидаемое значение в `LabControllerTest.applicationNameMatchesTicket`, запустите `./mvnw.cmd -B -ntp test` и перезапустите приложение. Новое имя действует после перезапуска; тестовое значение служит проверкой и не читается приложением. Для отката восстановите оба файла из предыдущего коммита и снова перезапустите приложение. Историю изменения показывает `git log -- src/main/resources/application.yml src/test/java/ru/rbpo/lab1/LabControllerTest.java`.

Текущий номер проверен тестом и журналом запуска. Отдельная пробная замена номера и откат не выполнялись.

Никаких секретов, расписания обновления, резервной копии базы данных или миграции данных у этого приложения нет. Доступность сервера определяется успешным запуском и HTTP-ответом; «свежесть данных» к статическим ответам неприменима. При сбое сначала проверьте журнал запуска, затем свободный порт и результат Maven-тестов. Релиз — запуск проверенного jar; для отката к прежней версии используйте соответствующий Git-коммит и пересоберите его.

## Руководство разработчика: точка расширения

Цель: добавить третий GET-маршрут без изменения существующих двух. Доступ: запись в репозиторий, JDK 17+, PowerShell в корне проекта. Предусловие: `./mvnw.cmd -B -ntp test` проходит до изменения.

1. В `src/main/java/ru/rbpo/lab1/LabController.java` добавьте новый метод с `@GetMapping("/new-route")` и определённым JSON-контрактом. Не меняйте пути M-02 и M-03.
2. В `src/test/java/ru/rbpo/lab1/LabControllerTest.java` добавьте проверку HTTP-статуса, типа/значения JSON и ошибочного случая, если он применим.
3. Обновите контракт в `docs/spec-v1.md` новой версией спецификации, внесите метод в реестр выше и поправьте пользовательское/эксплуатационное описание. Если появится расчёт, присвойте формуле стабильный ID и укажите единицы и округление.
4. Из корня запустите `./mvnw.cmd -B -ntp test`; ожидаются прежние четыре пройденных теста и новый тест. Затем проверьте живой маршрут через `Invoke-RestMethod`.
5. Перед публикацией просмотрите `git diff`, исключите секреты и локальный `target/`, зафиксируйте изменение и отправьте в GitHub. При регрессии верните изменённые файлы к предыдущему коммиту и повторите тесты.

Третий маршрут здесь описан как процедура, не реализован и не проверен в текущей версии. При добавлении внешних данных, приватной информации или новых ролей отдельно пересмотрите авторизацию, валидацию, ошибки и резервное копирование.

## Безопасность и сопровождение

Версия проверки: 1, 2026-09-19. Активы — исходники и номер билета в конфигурации; HTTP-вход — два фиксированных GET без параметров. Секретов и приватных данных приложение не хранит. Доступ к публичным маршрутам не ограничен, что соответствует учебному примеру; это не проверка всего OWASP ASVS и не оценка внешней сети. Результаты проверки 97 зависимостей и ограничения приведены в [журнале безопасности](docs/security-v1.md). Перед каждым обновлением зависимостей проверяйте официальные исправления Spring Boot, Maven и Java, выполняйте тесты и просматривайте `git diff`. При компрометации доступа к GitHub отзовите соответствующий токен или сеанс в настройках аккаунта и проверьте историю коммитов. Журнал запуска не должен содержать секретов; если появятся секреты, храните их вне Git.
