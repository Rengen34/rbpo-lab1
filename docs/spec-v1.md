# Спецификация v1 — лабораторная работа 1

Дата: 2026-09-19. Статус: реализация по видимым требованиям; номер билета предоставлен владельцем.

## Назначение и контекст

Студенту нужен небольшой публичный Java-проект для демонстрации Spring Boot, Maven и двух разных GET-запросов. Входная точка пользователя — HTTP API; результат сдачи — ссылка на опубликованный репозиторий GitHub. На момент постановки задания локальный репозиторий был пуст.

Система состоит из одного приложения Spring Boot со встроенным Jetty. Его контроллер возвращает статические учебные данные; внешних баз данных, очередей и интеграций нет. Maven собирает приложение и запускает тесты. GitHub хранит исходники, а ЛМС принимает ссылку от студента.

## Термины, компоненты и контракты

- **Приложение** (`LabApplication`) запускает Spring Boot и читает `application.yml`.
- **Контроллер** (`LabController`) обслуживает два публичных HTTP GET. Он не хранит состояние и не принимает пользовательские данные.
- **Сообщение**: `GET /api/message` → `200`, JSON `{"message":"Проект работает"}`.
- **Числа**: `GET /api/numbers` → `200`, JSON `{"numbers":[1,2,3]}`.
- **Конфигурация**: `spring.application.name` — строка `1БКС24106`, равная номеру билета; секретом не является. Изменение требует изменения файла и перезапуска приложения.

Инварианты: маршруты различаются; ответы стабильны; отсутствие базы данных не должно мешать запуску. Совместимость с прежними клиентами не требуется, поскольку приложение создаётся впервые. Публикация не должна включать секреты или локальные сборочные файлы.

## Приёмочные сценарии

1. **Сообщение:** дан запущенный проект; когда клиент выполняет `GET /api/message`; тогда он получает HTTP 200 и JSON с текстом `Проект работает`.
2. **Числа:** дан запущенный проект; когда клиент выполняет `GET /api/numbers`; тогда он получает HTTP 200 и JSON с массивом `[1,2,3]`.
3. **Неизвестный путь:** дан запущенный проект; когда клиент выполняет `GET /api/unknown`; тогда он получает HTTP 404, без подмены ответа одного из двух маршрутов.
4. **Название приложения:** дан номер билета в `application.yml`; когда приложение запускается; тогда `spring.application.name` доступен как это значение.

## Ошибки, безопасность и эксплуатация

HTTP API не принимает входных параметров, не обрабатывает персональные данные и не вызывает внешние сервисы. Основная граница доверия — входящий HTTP-запрос; разрешены только два фиксированных маршрута. Обработку неизвестного пути оставляем стандартной для Spring MVC. Секреты не сохраняются в репозитории. Публичный учебный API не вводит аутентификацию; если позже появятся данные пользователя, нужен отдельный пересмотр доступа.

Операционный сбой на этапе сборки или запуска выявляется ненулевым кодом Maven либо сообщением Spring Boot. Порт по умолчанию — 8080; его занятость диагностируется по журналу запуска. Состояния обновления данных здесь нет: ответы статические.

## Решения и порядок работ

1. Создать минимальную структуру Maven и два Java-компонента.
2. Добавить номер билета в единственный конфигурационный файл.
3. Добавить поведенческие HTTP-тесты и запустить их локально.
4. Обновить README с инструкцией пользователя, администратора и разработчика, проверить описанные команды.
5. Провести просмотр читаемости и затронутой поверхности безопасности.
6. Опубликовать проверенный проект на GitHub и передать ссылку для ЛМС.

Обоснование: один контроллер достаточен для двух статических функций; дополнительные слои и хранилище не улучшают этот учебный сценарий. Выбраны JSON-ответы, чтобы результат каждого маршрута был однозначно проверяемым. Возможная альтернатива — простой текст; JSON выбран как привычный REST-контракт. Jetty заменил встроенный сервер по умолчанию после проверки опубликованных уязвимостей его зависимостей; HTTP-контракт не менялся. Версии Jackson и Log4j закреплены на исправленных выпусках, совместимых с текущей веткой Spring Boot.

## Самопроверка спецификации

- **Архитектура:** у компонентов ясные обязанности, циклических зависимостей нет.
- **Тестирование:** каждое локально проверяемое требование имеет конкретный тест или команду; публикация и ЛМС требуют отдельного подтверждения.
- **Эксплуатация:** конфигурация и диагностика запуска описаны, миграция данных не нужна.
- **Безопасность:** входные данные отсутствуют, секреты не нужны; публичность GitHub требует просмотра файлов перед публикацией.

Материальных противоречий в видимой части задания не найдено. Это авторская самопроверка, не независимая экспертиза.
