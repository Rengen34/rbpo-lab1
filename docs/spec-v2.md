# Спецификация v2 — внутренние закупки

Дата: 2026-09-19. Основание: видимая страница `variant_24.pdf`, вариант 24. Контракт v2 зафиксирован до реализации и проверен после неё. Эта работа продолжает приложение лабораторной 1; её два прежних GET-адреса сохраняются.

## Назначение и границы

Пользователь учебного HTTP API ведёт заявки на закупку, поставщиков, коммерческие предложения, закупочные заказы и пользователей системы. Клиент отправляет JSON в Spring MVC; контроллеры сопоставляют адреса и ответы, `ProcurementService` проверяет правила, `InMemoryProcurementRepository` хранит записи в памяти. `Clock` передаёт сервису текущее время сервера. Внешних источников, входа по паролю и базы данных нет. После перезапуска записи исчезают.

Это один процесс: HTTP-клиент → пять контроллеров → один сервис закупок → хранилище пяти коллекций. Контроллеры не принимают решений о связях, а хранилище не решает бизнес-правила. Все операции сервиса выполняются под одним монитором, чтобы проверка связей и запись не расходились при параллельных запросах.

## Требования видимой страницы

| ID | Требование | Контракт и проверка |
| --- | --- | --- |
| L2-01 | Пять операций для каждой из пяти сущностей | 25 маршрутов из таблицы ниже; HTTP-тесты списка, элемента, создания, изменения и удаления |
| L2-02 | Чтение 200, создание 201 с `id`, изменение 200, удаление 204 | HTTP-статусы, JSON-тела и пустое тело удаления проверяются тестами |
| L2-03 | Удаление не оставляет недействительных ссылок | Для связанного объекта удаление отклоняется с 409; тесты проверяют сохранность графа |
| L2-04 | Текущее время определяет сервер | `createdAt` и `updatedAt` берутся из внедрённого `Clock`; клиент не может передать эти поля |
| L2-05 | HTTP, логика и хранение разделены | Контроллеры, сервис и репозиторий имеют отдельные файлы и обязанности |
| L2-06 | Сохранить результат первой лабораторной | Прежние два адреса, `spring.application.name=1БКС24106` и четыре теста продолжают работать |

Для каждого имени ресурса работают `GET /api/{resource}`, `GET /api/{resource}/{id}`, `POST /api/{resource}`, `PATCH /api/{resource}/{id}`, `DELETE /api/{resource}/{id}`. Имена ресурсов: `users`, `purchase-requests`, `suppliers`, `commercial-offers`, `purchase-orders`. JSON использует имена полей в `camelCase`. Список возвращается как массив; если записей нет, это `[]`.

## Поля и правила

| Ресурс | Поля JSON при создании | Правила |
| --- | --- | --- |
| Пользователь | `name` | Непустое имя; это учебная запись, не учётная запись для входа |
| Заявка | `authorId`, `description`, `maxAmount`, `status` | Автор существует; описание и статус непустые; сумма положительная |
| Поставщик | `name`, `category`, `admitted` | Название и категория непустые; признак допуска — обязательное `true`/`false`, отсутствие поля даёт 400 |
| Предложение | `purchaseRequestId`, `supplierId`, `price`, `deliveryDays`, `validityDays` | Заявка и поставщик существуют; цена и оба срока положительные |
| Заказ | `purchaseRequestId`, `selectedOfferId`, `fulfillmentStatus` | Заявка и предложение существуют; предложение относится к этой заявке; статус непустой |

Срок поставки и срок действия заданы в днях положительными целыми числами. Единицы в задании не уточнены; это выбранный учебный формат. Статусы — непустые строки без дополнительных переходов: допустимые значения в задании не перечислены. Признак допуска хранится, но ограничение на создание предложения по этому признаку не добавлено, поскольку такого правила нет в задании. Денежные суммы передаются десятичными числами, сохраняются без округления; формул нет.

Все записи получают положительный числовой `id`, уникальный в пределах своего ресурса, а также `createdAt` и `updatedAt` в UTC. Эти три поля задаёт сервер и в запросе запрещены. При `PATCH` передают непустой набор только изменяемых полей; остальные значения сохраняются. Явный `null`, неизвестное поле, пустая строка, неположительные сумма или срок дают 400. Чтение/изменение/удаление отсутствующей записи даёт 404. Ссылка на отсутствующую запись даёт 404; несовместимое предложение для заказа и попытка удалить объект со ссылками дают 409. Ошибка не должна частично менять данные. Ошибки логики возвращают короткий JSON `{"error":"INVALID_INPUT|NOT_FOUND|CONFLICT","message":"понятная причина"}` без стека вызовов и внутренних данных.

Удалять связанные записи можно после удаления зависимых в порядке: заказ → предложение → заявка/поставщик → пользователь. Переназначение предложения другой заявке запрещено, пока на него ссылается заказ для прежней заявки. На `PATCH` заказа вновь проверяется соответствие предложения заявке.

## Примеры приёмки

1. **Создание:** дан пользователь `id=1`; когда клиент создаёт заявку с `authorId=1`, описанием, положительной суммой и статусом; тогда ответ 201 содержит серверный `id` и время создания, а `GET` по новому адресу возвращает 200 и ту же заявку.
2. **Полная цепочка:** даны заявка и поставщик; когда клиент создаёт предложение для них, а затем заказ с этим предложением и той же заявкой; тогда каждый `POST` возвращает 201, а списки и чтение по `id` возвращают связанный граф.
3. **Частичное изменение:** дана заявка; когда клиент меняет только `status`; тогда ответ 200 содержит новый статус и прежние `authorId`, `description`, `maxAmount`.
4. **Целостность:** дан заказ, ссылающийся на предложение; когда клиент удаляет это предложение; тогда ответ 409 и оба объекта остаются доступны. После удаления заказа предложение можно удалить с ответом 204; повторное чтение даёт 404.
5. **Время и ввод:** когда клиент передаёт `createdAt`, `updatedAt`, `id` или `currentTime` в теле записи; тогда ответ 400 и запись не создаётся. При корректном запросе время в ответе соответствует часам сервера.
6. **Неудачное изменение:** когда клиент пытается заменить ссылку на отсутствующий объект или удалить связанный объект; тогда он получает 404/409 и повторное чтение показывает прежние данные.
7. **Совместимость:** когда клиент обращается к `/api/message` и `/api/numbers`; тогда прежние JSON-ответы и статусы 200 не меняются, а имя приложения остаётся `1БКС24106`.

## Решения и проверка проекта

Выбраны коллекции в памяти, поскольку видимое задание допускает коллекции или БД; это уменьшает установку зависимостей для учебной работы. Удаление связанных объектов отклоняется с 409 вместо каскада: клиент явно решает порядок, а данные не теряются незаметно. Внутренние записи неизменяемы, поэтому ответы — снимки на момент запроса. Входящий JSON является недоверенным: контроллер связывает только разрешённые поля, сервис проверяет значения и ссылки. У приложения нет входа по паролю; по умолчанию сервер слушает только `127.0.0.1`. Для реальных закупочных данных необходимы отдельные меры доступа и постоянное хранилище.

Самопроверка архитектуры: одна служба владеет межресурсными правилами и синхронизацией; контроллеры не получают прямой доступ к коллекциям. Самопроверка тестирования: сценарии покрывают каждый тип маршрута и ошибки 400/404/409. Самопроверка эксплуатации: перезапуск теряет данные, это явно указано в руководстве. Самопроверка безопасности: нет секретов и внешних вызовов; неизвестные поля и чужие серверные поля отвергаются. Это авторская проверка, не независимая экспертиза.

Порядок работы: 1) зафиксировать этот контракт; 2) добавить модели, часы и репозиторий; 3) добавить сервис и контроллеры; 4) проверить тестами 25 маршрутов, связи и старые адреса; 5) проверить реальные HTTP-запросы; 6) обновить руководство, эксплуатационные заметки и отчёт.

Реализация L2-01 и L2-02: пять классов `*Controller` и публичные методы `ProcurementService`; тест `ProcurementApiTest.completeResourceLifecycle`. L2-03: методы удаления в сервисе и `incompatibleOffersAndLinkedDeletesPreserveGraph`. L2-04: `ProcurementClockConfiguration.procurementClock`, создание/изменение в сервисе, `completeResourceLifecycle` и `rejectsInvalidAndServerOwnedFields`. L2-05: отдельные контроллеры, `ProcurementService`, `InMemoryProcurementRepository`. L2-06: неизменённые `LabController` и четыре теста `LabControllerTest`.
